# 主視窗版面優化設計：方向 A ＋ 漸進式收合來源

- 日期：2026-06-23
- 狀態：設計核可，待寫實作計畫
- 相關 TODO：取代 `shared-source-bar` 任務（見「與既有任務關係」）
- 前置：`tool-tabs-layout`（全寬 TabControl）已完成

## 背景與問題

`tool-tabs-layout` 完成後，主視窗由上而下為：自製頁首 → 更新通知 → TabControl →
來源設定列 → Log。實際使用後發現三個問題：

1. **自製頁首重複**：頁首僅有 App icon（28×28）與文字「影格整理工具」，
   與 Windows 原生標題列的 `Title` 與 `Icon` 完全相同，無任何互動或狀態，
   純佔約 54px 垂直空間。
2. **來源列動線顛倒**：來源設定列被放在 TabControl 下方（接近視窗底部），
   但實際操作流程是「先選來源資料夾 → 再用工具」，由上而下的視覺順序與操作順序相反。
3. **來源列長期佔位浪費**：資料夾與掃描格式通常一個 session 只設定一次，
   之後幾乎不再調整，卻長期佔用一整列（路徑 + 三顆按鈕 + 格式 pills 兩排），
   壓縮預覽空間。

## 目標

- 移除與原生標題列重複的視覺元素。
- 讓版面順序符合操作動線：來源 → 工具 → 預覽 → Log。
- 來源設定改為「平常精簡、需要時展開」，把空間還給預覽。

## 設計決策

### 1. 移除自製頁首

刪除 `Grid.Row="0"` 的頁首 Border。產品識別交給 Window 既有的
`Title="影格整理工具"` 與 `Icon`。回收的垂直空間給主內容。

### 2. 來源設定：頂部漸進式收合（progressive disclosure）

來源區移到 TabControl **上方**，並依狀態切換兩種型態：

- **未設來源（空狀態）**：展開且顯眼，作為引導第一步，含拖放提示與「選擇資料夾」，
  下方顯示掃描格式 pills。
- **已設來源（收合常態）**：縮成單行 chip，顯示
  `📁 <資料夾名> · <張數> · <主要格式> | <完整路徑>`，右側「✎ 變更 ▾」。
- **展開（點「✎ 變更 ▾」）**：展開為一行橫列，含路徑 TextBox、選擇／重新掃描／清空、
  完整格式 pills 與「包含子資料夾」，右側「▲ 收合」。

收合狀態由一個 `IsSourceExpanded` bool 控制；未設來源時強制展開（空狀態樣式）。

### 3. 版面順序

由上而下：

1. 來源 chip／橫列（依狀態收合或展開）
2. TabControl（4 個工具分頁，底線強調）— 主內容，佔 `*` 高度
3. 每個 TabItem 內：左欄純工具參數（約 260px）＋ 右側預覽全高
4. 左欄底部釘住「產生預覽 / 執行」，執行用實心強調色
5. Log（可摺疊）

## 元件與狀態

| 元件             | 狀態                          | 行為                                              |
| ---------------- | ----------------------------- | ------------------------------------------------- |
| 來源區           | 空狀態 / 收合 chip / 展開橫列 | `IsSourceExpanded` + `SelectedFolder` 是否為空驅動 |
| chip 摘要文字    | 隨掃描結果更新                | 綁定 `SelectedFolder`、`FileSummary`、已選格式    |
| 「✎ 變更 ▾」     | 收合時顯示                    | 切 `IsSourceExpanded = true`                      |
| 「▲ 收合」       | 展開時顯示                    | 切 `IsSourceExpanded = false`                     |
| 左欄主動作       | 釘底                          | 既有 `產生預覽` / `執行` command，CanExecute 不變 |

來源相關綁定（`SelectedFolder`、`FileSummary`、`IncludePng…`、`IncludeSubfolders`、
`BrowseFolderCommand`、`ScanFilesCommand`、`ClearFolderAndFilesCommand`）皆沿用既有
`MainViewModel`，不改 service 與 planner。

## 與既有任務關係

本設計**取代** TODO 中的 `shared-source-bar`（原規劃：來源列收進每個 TabItem 底部）。
原方案會讓來源在 4 個分頁各複製一份且仍長期佔位；本方案改為單一頂部收合區，
更省空間且無重複。`shared-source-bar` 任務應標記為被取代並改寫為本設計的任務。

預覽區塊在 4 個 TabItem 各複製一份的內部重複問題，本設計**不處理**，另開任務。

## 行為與邊界

- 切換分頁時，來源 chip 狀態與展開／收合狀態保持不變。
- 視窗縮到 `MinWidth=900`：展開橫列的格式 pills 可換行，不溢出。
- 批次執行中（縮放／降噪）：來源區的選擇／掃描／清空按鈕停用，chip 仍可見。
- 拖放資料夾到預覽區的既有行為不變。

## 測試與驗收

XAML 版面行為以手動驗收為主（沿用既有 service／planner，無新核心邏輯）：

- 既有 `dotnet test` 全數通過。
- 未設來源 → 顯示空狀態引導；設定後 → 自動收合成 chip。
- 點「✎ 變更 ▾」展開、「▲ 收合」收回；切分頁狀態保持。
- `MinWidth=900` pills 換行不溢出。
- 批次執行中來源按鈕正確停用。

若收合狀態需要由 ViewModel 計算（例如空狀態判定），該判定邏輯應可單元測試。

## 範圍邊界（YAGNI）

- 不做自訂標題列（隱藏原生 chrome）—— 另一個大改，目前無需求。
- 不處理預覽區塊 ×4 重複 —— 內部重構，另開任務。
- 不改 service、planner、檔案操作邏輯。
